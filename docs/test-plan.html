每項功能該怎麼驗：測試規格與案例對照

你問的是對的：這個專案目前沒有測試規格。這份把缺口攤開，並給出每項功能對應的測試案例、由誰執行、以及什麼時候跑。

16 個自動測試已上線

兩批自動測試全數通過，測試總數從 155 增為 171。過程中抓到一個真實缺陷：介面縮放原本會接受 0 或負數這種無效設定值，那會讓整個畫面塌掉，現在已擋下。剩下的都是必須用眼睛看或在車上驗的項目。

測試規格 已建立 44 個測試案例，逐項標明驗證方式與執行時機。
自訂功能覆蓋 邏輯與儲存都已守住 切換順序、設定儲存、縮放換算都有自動測試把關，剩畫面外觀靠人眼。
既有基礎設施 現成可用 上游附帶 22 個單元測試與 9 個裝置測試，也有自動化流程，直接沿用不必從零建。
基準測試 155 案全過 今天首次執行上游測試套件，零失敗零略過，基準線乾淨。

寫測試當場的收穫

兩件事值得記錄。其一，原本的縮放程式會照單全收任何數值，若設定檔被寫入 0 或負數，整個畫面會塌掉；寫測試時發現並補上了範圍檢查。其二，我第一版測試自己寫錯了斷言，以為按四次回到原點，實際是三次——測試當場擋下這個錯誤。這正是自動測試的價值：它不只驗程式，也驗我們對功能的理解。

剩下沒自動化的，是「按鍵長什麼樣、有沒有破版、車上好不好按」這類必須用眼睛和手驗的項目。要把這些也自動化，得建一個手機模擬器環境、每次跑數分鐘，建議等功能穩定後再評估，現階段用檢查表更划算。

五、必須承認的四件事

  • 先前的回報用詞不夠精確。我說過「編譯與程式碼規範皆通過」，那是事實，但它容易被讀成「功能沒問題」。實際上到目前為止，沒有任何一項功能被驗證過行為正確。
  • 自動測試守不到外觀。16 個自動測試涵蓋切換順序、設定儲存與縮放換算，但「按鍵有沒有真的畫出來」「150% 會不會破版」電腦驗不到，只能靠手動檢查表。這是目前最大的殘餘風險，也是上車前務必跑一次檢查表的原因。
  • 有些項目本質上無法自動化。實車、藍牙媒體鍵、手機廠商省電機制殺背景服務，這三類只能人工驗，這是限制不是偷懶。
  • 上游測試套件到今天才第一次跑。結果是 155 個測試案例全數通過、零失敗，代表這個 fork 的基準線乾淨，我們新增的程式碼沒有弄壞原有邏輯。但這 155 案沒有一項碰到循環記憶或介面縮放，所以它證明的是「沒改壞舊的」，不是「新的做對了」。
